# คู่มือ Use Case ทดสอบระบบ POS ร้านอาหาร

**เจ้าของเอกสาร:** ผู้จัดการร้าน / ทีมพัฒนาระบบ  
**ผู้ใช้เอกสาร:** พนักงาน, แอดมิน, ผู้จัดการกะ, ผู้ทดสอบระบบ  
**เวอร์ชัน:** 1.0  
**วันที่จัดทำ:** 26 สิงหาคม 2026  
**รอบทบทวน:** ทุกครั้งที่เพิ่มเมนู อุปกรณ์ วิธีชำระเงิน หรือปรับสิทธิ์ผู้ใช้

เอกสารนี้เป็น checklist สำหรับทดสอบ POS ตั้งแต่เปิดร้าน รับออเดอร์ ส่งงานไปยังครัว/บาร์ ชำระเงิน ปิดกะ ตรวจสต็อก ไปจนถึงกรณีผิดปกติและอุปกรณ์ขัดข้อง ใช้ได้ทั้งทดสอบก่อนเปิดร้าน, ทดสอบหลังแก้บั๊ก และทดสอบก่อนขึ้น production

> หลักสำคัญ: ใช้ข้อมูลทดสอบเท่านั้น ห้ามใช้บัตรจริง เงินจริง หรือส่งออเดอร์จริงเข้าครัวระหว่างการทดสอบ

## 1. วิธีอ่านและวิธีบันทึกผล

สถานะของแต่ละกรณีให้ใช้เพียงค่าใดค่าหนึ่ง:

- **ผ่าน** — ผลที่เกิดขึ้นตรงตามคาด ไม่มีข้อมูลซ้ำหรือข้อมูลหาย
- **ไม่ผ่าน** — ผลต่างจากคาด, ระบบค้าง, ยอดเงิน/สต็อกผิด หรือผู้ไม่มีสิทธิ์ทำรายการได้
- **รอแก้** — พบปัญหาแล้ว มีผู้รับผิดชอบและกำหนดวันแก้
- **ไม่เกี่ยวข้อง** — ฟังก์ชันหรืออุปกรณ์นั้นไม่ได้เปิดใช้ในสาขานี้

บันทึกทุกเคสด้วยรูปแบบนี้:

```text
วันที่/เวลา:
รหัสเคส:
ผู้ทดสอบ/อุปกรณ์:
ขั้นตอนที่ทำ:
ผลที่คาดหวัง:
ผลที่เกิดขึ้นจริง:
สถานะ:
รูปหน้าจอ/เลขออเดอร์/เลขใบเสร็จ:
ปัญหาและวิธีแก้ชั่วคราว:
ผู้รับผิดชอบและกำหนดแก้:
```

## 2. ผังระบบและอุปกรณ์ที่ต้องเตรียม

### 2.1 อุปกรณ์ขั้นต่ำ

| รหัส | จุดใช้งาน | หน้าที่ | สิ่งที่ต้องตรวจ |
|---|---|---|---|
| POS-01 | เครื่อง POS หลักหน้าร้าน | รับออเดอร์/รับเงิน | หน้าจอ, touch, login, network, เวลา, แบต/ไฟ |
| POS-02 | เครื่อง POS แยกหรือแคชเชียร์ | รับออเดอร์/ชำระเงิน/สำรอง | ใช้บัญชีและกะที่ถูกต้อง, ไม่เห็นข้อมูลเกินสิทธิ์ |
| ADM-01 | คอมพิวเตอร์หรือเว็บแอดมิน | จัดการเมนู ราคา ผู้ใช้ รายงาน | สิทธิ์, audit log, export, backup |
| PRN-01 | เครื่องพิมพ์ใบเสร็จ | พิมพ์ใบเสร็จลูกค้า | กระดาษ, ความชัด, ภาษาไทย, เลขใบเสร็จไม่ซ้ำ |
| PRN-K | เครื่องพิมพ์ครัว | พิมพ์รายการเข้าครัว | แยกตามสถานี, พิมพ์ครั้งเดียว, ตัวใหญ่พออ่าน |
| PRN-B | เครื่องพิมพ์บาร์น้ำ | พิมพ์รายการเครื่องดื่ม | รายการ/หมายเหตุครบ, ไม่ปนกับครัว |
| KDS/PRN-H | ครัวร้อน | รับอาหารผัด/ต้ม/ทอด | สถานะรับงาน/เสร็จ/ยกเลิก |
| KDS/PRN-C | ครัวเย็น | รับสลัด/ของเย็น/เตรียมเย็น | ความเย็น/หมายเหตุ/ลำดับคิว |
| KDS/PRN-G | ครัวย่าง | รับเมนูย่างและระดับความสุก | ระดับความสุก/หมายเหตุไม่หาย |
| NET-01 | Router/Wi-Fi/LAN | เชื่อม POS และเครื่องพิมพ์ | IP, สัญญาณ, การกลับมาเชื่อมต่อ |
| CASH-01 | ลิ้นชักเงินสด | เปิดเมื่อรับเงินสด | เปิดเฉพาะรายการที่กำหนด, ยอดนับตรง |
| SCAN-01 | เครื่องสแกน QR/Barcode (ถ้ามี) | สแกนสมาชิก/สินค้า/ชำระเงิน | อ่านได้, ไม่ยิงซ้ำ |
| PAY-01 | QR/เครื่องรับบัตร (ถ้ามี) | รับชำระเงิน | success/fail/timeout/refund |

> **สถานะ EDC ปัจจุบัน:** ระบบมีโครงสร้าง payment และช่องทาง `scheme` สำหรับจำลองการชำระบัตร แต่ยังไม่เชื่อมต่อ EDC จริงของธนาคาร/ผู้ให้บริการใด เครื่องจริงต้องผ่านการเลือก protocol, sandbox, certification, settlement และ approval ก่อนเปิดใช้งาน

### 2.2 เส้นทางข้อมูลที่ต้องเห็น

```text
ลูกค้า/พนักงานรับออเดอร์
        ↓
POS-01 หรือ POS-02 → เลขออเดอร์เดียวกันทั้งระบบ
        ├→ PRN-K / KDS ครัวร้อน
        ├→ PRN-C / KDS ครัวเย็น
        ├→ PRN-G / KDS ครัวย่าง
        ├→ PRN-B / KDS บาร์น้ำ
        ├→ PRN-01 ใบเสร็จ
        └→ สต็อก / รายงาน / สมาชิก / audit log
```

## 3. บัญชีและข้อมูลทดสอบ

สร้างข้อมูลทดสอบแยกจากร้านจริง และติดป้ายชื่อว่า `TEST` ทุกเมนู/โต๊ะ/ผู้ใช้

### 3.1 ผู้ใช้ทดสอบ

| บทบาท | ความสามารถหลัก | สิ่งที่ห้ามทำโดยไม่อนุมัติ |
|---|---|---|
| พนักงาน | เปิดโต๊ะ, รับออเดอร์, แก้ไขก่อนยืนยัน, พิมพ์ใบเสร็จ | เปลี่ยนราคา, ลบออเดอร์ที่ชำระแล้ว, ปิดกะคนอื่น, ดูรายงานต้นทุน |
| หัวหน้ากะ | ทำรายการพนักงาน, ยกเลิก/คืนเงินตามวงเงิน, ปิดกะ | แก้สิทธิ์แอดมิน, แก้ audit log |
| แอดมิน | เมนู, ราคา, ภาษี, ผู้ใช้, สถานีครัว, รายงาน | ข้าม approval หรือแก้ข้อมูลย้อนหลังโดยไม่มีบันทึก |
| ลูกค้า QR | ดูเมนู, ส่งออเดอร์, ดูสถานะ, ใช้คูปอง/สมาชิก | เห็นออเดอร์หรือข้อมูลส่วนตัวของลูกค้าคนอื่น |
| ผู้ตรวจสอบ | อ่านรายงานและ log | แก้ไขข้อมูลธุรกรรม |

### 3.2 เมนูทดสอบ

เตรียมอย่างน้อย:

- อาหารครัวร้อน 1 รายการ: `TEST-ผัดกะเพรา`
- อาหารครัวเย็น 1 รายการ: `TEST-สลัด`
- อาหารครัวย่าง 1 รายการ: `TEST-สเต๊ก`
- เครื่องดื่มบาร์น้ำ 1 รายการ: `TEST-ชาเย็น`
- เมนูมีตัวเลือก: ระดับความเผ็ด, ระดับความสุก, เพิ่ม topping
- เมนูหมดสต็อก 1 รายการ
- เมนูราคา 0 บาทสำหรับทดสอบ comp/free
- สินค้าภาษีต่างกัน, ส่วนลดเป็นบาทและเปอร์เซ็นต์, คูปองหมดอายุ
- BOM ของแต่ละเมนู เช่น กาแฟ 1 แก้วตัดเมล็ดกาแฟ 18 กรัมและนม 150 มล.

ใช้ราคาง่ายต่อการตรวจ เช่น 100, 101, 1,999 บาท และจำนวนทศนิยมสำหรับวัตถุดิบ แต่ยอดเงินต้องคำนวณเป็นสตางค์และห้ามปัดผิด

## 4. เกณฑ์ผ่านระดับระบบ

ระบบจะถือว่าพร้อมใช้งานเมื่อ:

1. ออเดอร์หนึ่งรายการมีเลขเดียวกันใน POS, ครัว/บาร์, ใบเสร็จ, รายงาน และสต็อก
2. ทำรายการซ้ำ, กดปุ่มซ้ำ, refresh หรือกลับมาออนไลน์แล้วไม่เกิดออเดอร์/การตัดเงิน/การตัดสต็อกซ้ำ
3. ผู้ใช้ทำได้เฉพาะสิทธิ์ของตนเอง และทุกการยกเลิก/คืนเงิน/แก้ราคาอยู่ใน audit log
4. ยอดรวม, ส่วนลด, ภาษี, เงินทอน, เงินสดในลิ้นชัก และรายงานปิดกะตรงกัน
5. เครื่องพิมพ์แต่ละสถานีพิมพ์เฉพาะรายการของสถานีนั้น และงานที่ล้มเหลวมีวิธีพิมพ์ซ้ำที่ไม่สร้างออเดอร์ซ้ำ
6. เมื่ออุปกรณ์หรืออินเทอร์เน็ตขัดข้อง พนักงานมีขั้นตอนทำงานต่อและ sync กลับได้อย่างปลอดภัย

## 5. Use case ชุด A — Smoke test ก่อนเริ่มทดสอบเต็มรูปแบบ

| ID | กรณี | ขั้นตอนย่อ | ผลที่คาดหวัง |
|---|---|---|---|
| SM-01 | เปิดระบบ | เปิด router, POS, admin, printer | ทุกจุดพร้อม, เวลาและสาขาถูกต้อง |
| SM-02 | Login | พนักงาน login ด้วยบัญชีทดสอบ | เข้าได้เฉพาะหน้าที่มีสิทธิ์ |
| SM-03 | รับออเดอร์ 1 รายการ | เลือกอาหารร้อน 1 รายการ ยืนยัน | มีเลขออเดอร์และพิมพ์ไปครัวร้อน |
| SM-04 | รับชำระเงินสด | รับเงินพอดี | ใบเสร็จออก, สถานะ COMPLETED, ลิ้นชักเปิด |
| SM-05 | รับชำระ QR | สแกน QR ทดสอบและรอ success | ชำระครั้งเดียว, ใบเสร็จออก |
| SM-06 | ปิดกะ | นับเงินตามยอด | ปิดกะสำเร็จและ variance ถูกต้อง |

ถ้า SM-01 ถึง SM-06 ไม่ผ่าน ให้หยุดทดสอบชุดใหญ่ แก้ตามตารางปัญหาด่วนท้ายเอกสารก่อน

## 6. Use case ชุด B — พนักงานหน้าร้าน: กรณีปกติ

| ID | สถานการณ์และขั้นตอน | ผลที่คาดหวัง |
|---|---|---|
| EMP-01 | Login → เลือกสาขา/จุดขาย → เปิดกะพร้อมเงินทอน | เห็นสาขาถูกต้อง, เงินตั้งต้นถูกบันทึก, เวลาเปิดกะอยู่ในระบบ |
| EMP-02 | เปิดโต๊ะ/เลือกทานที่ร้าน → เพิ่มอาหารร้อน เย็น ย่าง และเครื่องดื่ม | ระบบแยก ticket ตามสถานีโดยยังใช้เลขออเดอร์เดียวกัน |
| EMP-03 | ใส่ modifier เช่น ไม่เผ็ด, สุก medium, ไม่ใส่น้ำแข็ง | หมายเหตุแสดงบน POS และใบครัว/บาร์ครบ |
| EMP-04 | บันทึกพักออเดอร์ → เรียกกลับมาแก้ไข → ยืนยัน | ยอดไม่เปลี่ยนเองและไม่มีออเดอร์ซ้ำ |
| EMP-05 | เพิ่มรายการหลังส่งครัว | พิมพ์เฉพาะรายการเพิ่ม, ไม่พิมพ์ของเดิมซ้ำ |
| EMP-06 | ทำรายการกลับบ้าน/ทานที่ร้าน | ภาษี/ค่าบรรจุภัณฑ์/พิมพ์ใบเสร็จถูกตามประเภท |
| EMP-07 | แบ่งบิลตามรายการ | แต่ละบิลมีรายการและยอดถูกต้อง รวมกันเท่าบิลเดิม |
| EMP-08 | รวมโต๊ะ/ย้ายโต๊ะ | เลขออเดอร์และรายการไม่หาย ไม่ซ้ำ รายงานสะท้อนโต๊ะใหม่ |
| EMP-09 | รับเงินสดมากกว่ายอด | เงินทอนถูกต้อง ลิ้นชักเปิด ใบเสร็จระบุช่องทางเงินสด |
| EMP-10 | รับเงินสดพอดี | เงินทอนเป็น 0 ไม่แสดงค่าติดลบ |
| EMP-11 | รับ QR/บัตรสำเร็จ | สถานะชำระสำเร็จและไม่เปิดช่องทางอื่นซ้ำ |
| EMP-12 | ออกใบเสร็จซ้ำ | ได้สำเนาใบเดิมพร้อมคำว่า copy/reprint และไม่ตัดเงินซ้ำ |
| EMP-13 | ลูกค้าขอใบกำกับภาษี | เก็บข้อมูลตามที่กำหนดและออกเอกสารที่อ้างอิงเลขออเดอร์เดียวกัน |
| EMP-14 | ปิดกะและนับเงินจริง | ระบบคำนวณยอดคาดหวัง, ส่วนต่าง และให้ใส่เหตุผลเมื่อไม่ตรง |

## 7. Use case ชุด C — พนักงาน: กรณีพิสดารและความผิดพลาดที่ต้องรับมือ

| ID | สถานการณ์ | ผลที่ต้องเกิด | วิธีปฏิบัติเมื่อไม่ผ่าน |
|---|---|---|---|
| EMP-X01 | กดชำระเงินซ้ำหรือแตะปุ่มสองครั้งเร็ว ๆ | มีธุรกรรมเดียว ใบเสร็จเดียว ยอดเดียว | ห้ามกดซ้ำ ให้ค้นหาเลขออเดอร์และตรวจสถานะก่อน; หากซ้ำให้กันเงินคืนและเปิด incident |
| EMP-X02 | QR timeout แต่เงินอาจถูกหัก | ออเดอร์ไม่ถูกปิดซ้ำและมีสถานะรอตรวจสอบ | ห้ามรับเงินช่องทางใหม่ทันที ตรวจ transaction reference ก่อน แล้วใช้เมนู verify/reconcile |
| EMP-X03 | ลูกค้าเปลี่ยนใจหลังส่งครัว | ยกเลิกได้ตามสิทธิ์และมีค่าเสียหาย/เหตุผลถ้าตั้งค่าไว้ | ให้หัวหน้ากะอนุมัติ ห้ามลบออเดอร์จากฐานข้อมูล |
| EMP-X04 | สินค้าหมดหลังรับออเดอร์ | ระบบแจ้งหมด/หยุดขาย และออเดอร์เดิมมีทางเลือกทดแทน | โทรแจ้งลูกค้า แก้เป็นรายการทดแทนหรือคืนเงินเฉพาะรายการ พร้อมบันทึกเหตุผล |
| EMP-X05 | ลูกค้าใช้ส่วนลดหลายอันซ้อนกัน | ใช้ได้เฉพาะตามกติกา ไม่ติดลบ | ตรวจลำดับส่วนลดและกฎ stacking; ปิดคูปองที่ใช้ซ้ำได้ทันที |
| EMP-X06 | ราคาเปลี่ยนระหว่างเปิดบิล | ออเดอร์ที่ยืนยันแล้วคงราคาตอนขาย | ห้ามแก้ฐานข้อมูลตรง ๆ ใช้ price override พร้อมสิทธิ์และ audit log |
| EMP-X07 | เงินทอนติดลบ/ยอดติดลบ | ระบบไม่ให้จบรายการ | ตรวจจำนวนเงินและวิธีชำระ ห้ามใช้การแก้ยอดด้วยมือโดยไม่มีเหตุผล |
| EMP-X08 | เปิดออเดอร์ค้างข้ามวัน | ระบบเตือนและไม่ทำให้รายงานวันใหม่ปนวันเก่า | ผู้จัดการตรวจรายการค้างและปิดด้วยเหตุผล ไม่ลบรายการ |
| EMP-X09 | ลูกค้าขอคืนบางรายการหลังชำระ | คืนเฉพาะรายการและปรับสต็อก/รายงานถูกต้อง | ทำ partial refund ผ่าน workflow; ห้ามสร้างออเดอร์ใหม่กลบรายการเดิม |
| EMP-X10 | พนักงานถูก logout ระหว่างทำรายการ | ออเดอร์ที่บันทึกแล้วไม่หาย; รายการที่ยังไม่ยืนยันไม่ถูกส่ง | login ใหม่แล้วค้นหา draft; ถ้าซ้ำให้ยกเลิก draft ที่ซ้ำก่อนส่ง |
| EMP-X11 | อินเทอร์เน็ตหลุด | ระบบแจ้ง offline และใช้ offline order ตามนโยบาย | จด local order ID, ห้ามเปิดหลายหน้าสร้างรายการเดียวกัน, sync หลังออนไลน์ |
| EMP-X12 | เวลาบน POS ผิด | ไม่ทำให้เลขใบเสร็จและปิดกะผิดวัน | หยุดรับชำระถ้ากระทบเอกสาร แก้ time sync แล้วตรวจรายการช่วงเวลานั้น |
| EMP-X13 | พนักงานพยายามเปลี่ยนราคา/คืนเงินโดยไม่มีสิทธิ์ | ระบบปฏิเสธและบันทึก audit log | ไม่แชร์รหัสหัวหน้ากะ ให้ผู้มีสิทธิ์ทำรายการแทน |

## 7.1 Use case สำคัญ: คืนบิล, ยกเลิกบิล และยกเลิกโต๊ะ

### ความหมายที่ใช้ในคู่มือนี้

| คำเรียก | ใช้เมื่อ | ผลทางบัญชี |
|---|---|---|
| **ยกเลิกบิล (Void/Cancel)** | ออเดอร์ยังไม่ชำระ หรือชำระแล้วแต่ต้องยกเลิกตามสิทธิ์/นโยบาย | ไม่ควรลบข้อมูลเดิม ต้องเก็บสถานะยกเลิก เหตุผล ผู้อนุมัติ และผลต่อสต็อก |
| **คืนบิล (Refund)** | บิลชำระเงินแล้วและร้านต้องคืนเงินเต็มบิลหรือบางรายการ | สร้างรายการคืนเงินอ้างอิง payment เดิม ไม่สร้างบิลใหม่กลบของเดิม |
| **ยกเลิกโต๊ะ** | ลูกค้าออก/ไม่ใช้โต๊ะ หรือโต๊ะมีบิลค้างที่ต้องจัดการ | เคลียร์สถานะโต๊ะหลังตรวจออเดอร์ค้าง ห้ามทำให้ออเดอร์หรือเงินหาย |

### ขั้นตอนปฏิบัติสำหรับพนักงาน

#### A. ยกเลิกบิลก่อนชำระเงิน

1. เปิดบิลเดิมจากเลขออเดอร์หรือโต๊ะ ห้ามสร้างบิลใหม่เพื่อกลบรายการ
2. กด **ยกเลิกบิล** และเลือกเหตุผล เช่น ลูกค้ายกเลิก, คีย์ผิด, โต๊ะผิด, เมนูหมด
3. ถ้าบิลถูกส่งไปครัว/บาร์แล้ว ให้ระบบส่งข้อความ **ยกเลิก** ไปยังทุกสถานีที่เกี่ยวข้อง
4. ให้หัวหน้ากะอนุมัติเมื่อเกินวงเงินหรือหลังครัวรับงานแล้ว
5. ตรวจว่าบิลเป็น `CANCELLED`, โต๊ะกลับเป็นสถานะว่างตามกติกา และไม่มี payment สำเร็จ
6. ตรวจสต็อก: ถ้ามีการตัดวัตถุดิบไปแล้ว ต้องมีรายการคืน/ปรับกลับตามสถานะจริง ห้ามตัดซ้ำ

#### B. ยกเลิกบิลหลังชำระเงิน

1. ค้นหาบิลจากเลขใบเสร็จและตรวจ payment reference ก่อนทุกครั้ง
2. ห้ามใช้ปุ่มยกเลิกแบบก่อนชำระ ให้เลือก **คืนบิล/Refund** หรือ workflow ยกเลิกหลังชำระ
3. เลือกคืนเต็มบิลหรือคืนเฉพาะรายการ พร้อมเหตุผลและผู้อนุมัติ
4. คืนเงินกลับช่องทางเดิมเป็นหลัก เช่น จ่าย QR ให้คืนผ่านกระบวนการ QR ตามนโยบาย
5. ตรวจว่าใบเสร็จเดิมยังอยู่ในประวัติ, มีเอกสารคืนเงินอ้างอิงเลขเดิม และสถานะ payment เป็น `REFUNDED` หรือ `PARTIALLY_REFUNDED`
6. ตรวจรายงานยอดขาย, เงินสด/ยอด settlement, ภาษี และสต็อกให้ปรับตรงกัน

#### C. คืนบิลเต็มบิล

1. เลือกบิลที่ชำระแล้ว → **คืนบิลเต็มจำนวน**
2. ตรวจยอดที่จะคืนและช่องทางเงินก่อนกดยืนยัน
3. ให้ผู้มีสิทธิ์อนุมัติ พร้อมระบุเหตุผล
4. ระบบต้องป้องกันการกดคืนซ้ำ โดยแสดงยอดที่คืนไปแล้ว
5. พิมพ์หรือบันทึกใบคืนเงิน และแจ้งลูกค้าตามช่องทางที่ร้านกำหนด

#### D. คืนบางรายการในบิล

1. เลือกเฉพาะรายการที่ต้องคืน ไม่เลือกทั้งบิลโดยไม่ตั้งใจ
2. ระบุจำนวนที่คืน เช่น สั่ง 2 ชิ้น คืน 1 ชิ้น
3. ตรวจส่วนลด/ภาษี/ค่าบริการที่ต้องปรับตามกติกา
4. ตรวจว่ารายการอื่นยังคงขายอยู่ และยอดคืนไม่เกินยอดที่จ่ายจริง
5. ตรวจสต็อก: ของที่ยังไม่ผลิตอาจคืนกลับได้; ของที่ทำเสร็จ/เสิร์ฟแล้วให้ใช้เหตุผลสูญเสียตามนโยบาย ไม่คืนสต็อกเท็จ

#### E. ยกเลิกโต๊ะ

1. เปิดหน้าผังโต๊ะและเลือกโต๊ะ
2. ระบบต้องแสดงก่อนว่าโต๊ะมีบิลเปิด, รายการส่งครัว, payment pending หรือไม่
3. ถ้าไม่มีบิลค้าง ให้เลือก **ยกเลิกการจอง/เคลียร์โต๊ะ** และยืนยันเหตุผล
4. ถ้ามีบิลค้าง ให้จัดการบิลก่อน: ยกเลิกบิลก่อนชำระ หรือคืนบิลหลังชำระ แล้วจึงเคลียร์โต๊ะ
5. ถ้ามีออเดอร์ไปครัวแล้ว ต้องแจ้งทุกสถานีให้หยุดทำ/ยกเลิกงาน
6. ตรวจว่าโต๊ะเปลี่ยนเป็น `AVAILABLE/CLEANING` ตาม flow ของร้าน ไม่ใช่แค่หายจากหน้าจอ
7. ตรวจว่าบิลเดิมยังค้นหาได้จากประวัติและมี audit log ระบุว่าใครยกเลิกโต๊ะ

### ตารางทดสอบเฉพาะ 3 เรื่องนี้

| ID | กรณีทดสอบ | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|---|
| CAN-01 | ยกเลิกบิลก่อนส่งครัว | เปิดบิล → ยกเลิก → ใส่เหตุผล | บิล cancelled, ไม่พิมพ์ครัว, โต๊ะว่าง, ไม่ตัดสต็อก |
| CAN-02 | ยกเลิกบิลหลังส่งครัว | เปิดบิล → ยกเลิก → อนุมัติ | ครัว/บาร์ได้รับ cancel, มีผู้อนุมัติ, ไม่สร้างบิลใหม่ |
| CAN-03 | ยกเลิกบิลที่ชำระแล้ว | ค้นหาใบเสร็จ → เลือก refund | ระบบไม่ให้ใช้ void ธรรมดา และสร้าง refund อ้างอิง payment เดิม |
| CAN-04 | คืนบิลเต็มบิล | refund full → ยืนยัน → ค้นหาอีกครั้ง | คืนได้ครั้งเดียว ยอดคืนถูก รายงานและสถานะตรงกัน |
| CAN-05 | คืนบางรายการ | เลือก 1 จาก 2 รายการ → refund | คืนเฉพาะรายการที่เลือก ยอดที่เหลือยังถูกต้อง |
| CAN-06 | กดคืนบิลซ้ำ | กด refund บิลเดิมอีกครั้ง | ระบบปฏิเสธหรือคืนได้เฉพาะยอดคงเหลือ ไม่จ่ายซ้ำ |
| CAN-07 | คืนเงินข้ามช่องทาง | บิลจ่าย QR แต่เลือกคืนเงินสด | ระบบปฏิเสธหรือบังคับ approval ตามนโยบายและบันทึกเหตุผล |
| CAN-08 | ยกเลิกโต๊ะว่าง | เลือกโต๊ะไม่มีบิล → ยกเลิก/เคลียร์ | โต๊ะเปลี่ยนสถานะถูกต้อง มี log และไม่กระทบยอดขาย |
| CAN-09 | ยกเลิกโต๊ะมีบิลค้าง | เลือกโต๊ะที่มีบิล → พยายามเคลียร์ | ระบบไม่ให้เคลียร์จนจัดการบิล และบอกขั้นตอนถัดไป |
| CAN-10 | ยกเลิกโต๊ะที่มีงานครัว | ยกเลิกบิล/โต๊ะหลังส่งครัว | ทุกสถานีได้รับ cancel และไม่มีรายการทำต่อโดยไม่รู้เหตุผล |
| CAN-11 | พนักงานไม่มีสิทธิ์ | พนักงานกด void/refund/clear table | ปฏิเสธ, ไม่เปลี่ยนข้อมูล, เก็บ audit log |
| CAN-12 | ยกเลิกแล้วเปิดโต๊ะใหม่ | ยกเลิกโต๊ะเดิม → เปิดออเดอร์ใหม่ | ออเดอร์ใหม่เลขใหม่ ไม่ปนกับบิลที่ยกเลิก |

### ถ้ากดผิด ให้ทำอย่างไร

- กด **ยกเลิกบิลผิดก่อนชำระ:** ห้ามสร้างบิลใหม่ทันที ให้หัวหน้ากะตรวจเลขเดิม แล้วใช้เมนู restore/reopen ถ้าระบบอนุญาต หรือสร้างออเดอร์ใหม่โดยอ้างอิงเลขเดิมในหมายเหตุ
- กด **คืนบิลผิดหลังชำระ:** ห้ามรับเงินลูกค้ากลับเข้าระบบเอง ให้หยุดรายการและแจ้งผู้จัดการ/บัญชีตรวจ payment reference ก่อนทำรายการชดเชย
- กด **ยกเลิกโต๊ะผิด:** ห้ามลบโต๊ะหรือบิล ให้ตรวจสถานะโต๊ะและออเดอร์เดิม แล้วเรียกคืนโต๊ะตาม workflow พร้อมบันทึกเหตุผล
- ทุกกรณีต้องตรวจว่าไม่มีการคืนเงินซ้ำ, ออเดอร์ซ้ำ, ใบครัวซ้ำ และสต็อกติดลบก่อนปิดเหตุการณ์

### 9.1 ตัวอย่างลูกค้าพิสดาร/สถานการณ์คาดเดายาก

คำว่า “พิสดาร” ในที่นี้หมายถึงสถานการณ์ที่ไม่ใช่ flow ปกติ ไม่ได้หมายความว่าต้องตอบโต้ลูกค้า ให้พนักงานยึดหลัก **สุภาพ–ตรวจสอบก่อน–ไม่ทำรายการซ้ำ–ให้หัวหน้ากะอนุมัติเมื่อเกี่ยวกับเงิน**

| ID | สถานการณ์ลูกค้า | สิ่งที่ระบบ/พนักงานต้องทำ | ห้ามทำ |
|---|---|---|---|
| CUS-X01 | ลูกค้าสั่งแล้วขอเปลี่ยนเมนูหลายครั้ง | แก้ draft ได้ก่อนยืนยัน; หลังส่งครัวใช้เพิ่ม/ยกเลิกพร้อมเหตุผล | ลบบิลเดิมหรือสร้างบิลใหม่กลบของเดิม |
| CUS-X02 | ลูกค้าอ้างว่าไม่ได้สั่งรายการในบิล | เปิด audit/order timeline และตรวจผู้ส่งจาก POS/QR ก่อนแก้ | คืนเงินทันทีโดยไม่ตรวจสอบ |
| CUS-X03 | ลูกค้าจ่ายแล้วแต่บอกว่ายังไม่ได้จ่าย | ตรวจ payment status, reference และ settlement ก่อนรับเงินใหม่ | ให้ลูกค้าจ่ายซ้ำเพราะหน้า POS ค้าง |
| CUS-X04 | ลูกค้าจ่ายบัตร/QR ซ้ำสองครั้ง | ค้นหา reference และยอดรายการซ้ำ แล้วทำ reconciliation/refund ตามสิทธิ์ | สร้าง refund แบบไม่มีหลักฐาน |
| CUS-X05 | ลูกค้าขอคืนเงินเต็มบิล แต่กินไปบางส่วนแล้ว | ให้หัวหน้ากะตรวจนโยบาย; คืนเฉพาะส่วนที่อนุมัติและบันทึกเหตุผล | คืนเต็มบิลโดยไม่บันทึกสาเหตุ |
| CUS-X06 | ลูกค้าขอเปลี่ยนจากทานที่ร้านเป็นกลับบ้านหลังคิดเงิน | คำนวณค่าบรรจุภัณฑ์/ภาษีใหม่ผ่าน adjustment workflow | แก้ยอดตรงฐานข้อมูลหรือเขียนทับใบเสร็จ |
| CUS-X07 | ลูกค้าหลายคนจ่ายบิลเดียวกัน คนละวิธี | ใช้ split bill/multiple tender และตรวจยอดรวมเท่าบิล | รับเงินแยกโดยไม่ผูกกับเลขบิล |
| CUS-X08 | ลูกค้าขอแยกบิลหลังชำระแล้ว | ตรวจว่านโยบายอนุญาตหรือไม่; ออกเอกสารอ้างอิงเดิม/ทำ refund และชำระใหม่อย่างมีหลักฐาน | ลบใบเสร็จเดิม |
| CUS-X09 | ลูกค้าขอใช้คูปองที่หมดอายุ/ใช้ไปแล้ว | ระบบต้องปฏิเสธพร้อมเหตุผล พนักงานเสนอทางเลือกตามนโยบาย | เปลี่ยนวันเครื่องหรือแก้คูปองเพื่อเอาใจลูกค้า |
| CUS-X10 | ลูกค้าขอส่วนลดพิเศษโดยอ้างว่าเป็นเจ้าของร้าน/คนรู้จัก | ให้ผู้มีสิทธิ์อนุมัติและบันทึกเหตุผล | แชร์รหัสผู้จัดการหรือกดส่วนลดลับ |
| CUS-X11 | ลูกค้าแพ้อาหาร/ขอเปลี่ยนส่วนผสม | แสดง allergen warning และส่งหมายเหตุเด่นไปสถานีที่ทำอาหาร | รับปากด้วยวาจาแต่ไม่บันทึกใน ticket |
| CUS-X12 | ลูกค้าขอให้ทำเมนูนอกสูตร/เพิ่มวัตถุดิบจำนวนมาก | ใช้ modifier/ราคาเพิ่มที่กำหนด; ถ้าไม่มีให้หัวหน้ากะอนุมัติ | พิมพ์หมายเหตุลอย ๆ จนราคาและสต็อกไม่ตรง |
| CUS-X13 | ลูกค้าอ้างว่าอาหารช้าแล้วขอฟรีทั้งหมด | ตรวจเวลารับออเดอร์/สถานะครัวก่อน ใช้ comp/ส่วนลดตามวงเงิน | แจกฟรีโดยไม่มี approval หรือเหตุผล |
| CUS-X14 | ลูกค้ารับอาหารผิดโต๊ะ/เรียกเลขออเดอร์ผิด | ตรวจเลขออเดอร์และชื่อรายการก่อนส่งมอบ | เปลี่ยนโต๊ะในระบบโดยไม่ตรวจบิล |
| CUS-X15 | ลูกค้าทิ้งโต๊ะโดยไม่จ่าย | เปลี่ยนสถานะเป็น suspected walkout, แจ้งผู้จัดการ, เก็บหลักฐานและปิดตาม policy | ลบออเดอร์เพื่อให้โต๊ะว่าง |
| CUS-X16 | ลูกค้าจองโต๊ะแต่ไม่มา แล้วมีลูกค้าใหม่มานั่ง | ตรวจเวลาจอง/สถานะมัดจำก่อนเคลียร์โต๊ะ | ยกเลิกโต๊ะโดยไม่ตรวจ deposit |
| CUS-X17 | ลูกค้าขอใบเสร็จย้อนหลังหลายวัน | ค้นจากเลขใบเสร็จ/วันที่/ยอด แล้วพิมพ์สำเนา | สร้างยอดขายหรือเลขใบเสร็จใหม่ |
| CUS-X18 | ลูกค้าขอใบกำกับภาษีแต่ข้อมูลไม่ครบ/ข้อมูลผิด | ให้ลูกค้ายืนยันข้อมูลและใช้เอกสารแก้ไขตามสิทธิ์ | แก้ชื่อ/เลขผู้เสียภาษีเงียบ ๆ หลังออกเอกสาร |
| CUS-X19 | ลูกค้าสั่งจาก QR พร้อมกันหลายเครื่อง | รวมตามกติกาโต๊ะและแสดงรายการที่ส่งแล้ว | ส่งรายการซ้ำเพราะแต่ละคนไม่เห็นกัน |
| CUS-X20 | ลูกค้าเปิด QR จากรูปเก่าหรือส่งลิงก์ให้คนนอก | ตรวจ token, โต๊ะ, สาขา และอายุ QR | รับออเดอร์โดยไม่ยืนยันโต๊ะ |
| CUS-X21 | ลูกค้าขอให้พนักงานเก็บข้อมูลบัตร/รหัสผ่านไว้ | ปฏิเสธอย่างสุภาพและใช้ช่องทางชำระปกติ | จดเลขบัตร, PIN, CVV หรือถ่ายรูปบัตร |
| CUS-X22 | ลูกค้าโวยวาย/กดดันให้ข้ามขั้นตอน | พนักงานหยุดรายการ เรียกหัวหน้ากะ และรักษาความปลอดภัยของข้อมูล | ให้รหัสแอดมินหรือยกเลิก audit |

### 9.2 ตัวอย่างบทพูดสั้นสำหรับพนักงาน

- **ลูกค้าบอกว่าจ่ายแล้วแต่ระบบยังไม่ขึ้น:** “ขอตรวจสอบเลขรายการให้ก่อนนะครับ/ค่ะ เพื่อป้องกันการคิดเงินซ้ำ รอสักครู่นะครับ/ค่ะ”
- **ลูกค้าขอคืนเงิน:** “ได้ครับ/ค่ะ ขอเช็กสถานะบิลและเรียกหัวหน้ากะอนุมัติตามขั้นตอนก่อนนะครับ/ค่ะ”
- **ลูกค้าขอใช้คูปองหมดอายุ:** “ระบบแจ้งว่าคูปองหมดอายุแล้วครับ/ค่ะ เดี๋ยวขอตรวจสอบโปรโมชันที่ยังใช้ได้ให้แทนนะครับ/ค่ะ”
- **ลูกค้าแจ้งแพ้อาหาร:** “รับทราบครับ/ค่ะ ผม/ดิฉันจะใส่หมายเหตุแพ้อาหารให้ครัวเห็นชัดเจน และขอยืนยันส่วนผสมอีกครั้งนะครับ/ค่ะ”
- **ลูกค้าเร่งให้ข้ามการตรวจสอบ:** “เพื่อป้องกันยอดผิดหรือชำระซ้ำ ขอเช็กในระบบก่อนสักครู่นะครับ/ค่ะ”

| FIN-10 | รายงานยอดรายวันเทียบใบเสร็จ | จำนวนรายการ, ยอดรวม, ช่องทางชำระ และ refund ตรงกัน |

## 12.1 Use case เชื่อมเครื่อง EDC (เครื่องรับบัตร)

### ภาพการทำงานที่ต้องการ

```text
POS ส่งยอดเงิน + เลขอ้างอิงเฉพาะรายการ
        ↓
EDC แสดงยอดให้ลูกค้าตรวจ → แตะ/เสียบ/รูดบัตร → PIN/อนุมัติ
        ↓
EDC ส่งผลสำเร็จ/ไม่สำเร็จ + approval code + transaction reference
        ↓
POS ตรวจผลและ idempotency → ปิดบิล → ออกใบเสร็จ
```

### ขอบเขตที่ต้องตกลงก่อนเชื่อมเครื่องจริง

| เรื่อง | ต้องกำหนดให้ชัด |
|---|---|
| ผู้ให้บริการ | ธนาคาร/ผู้ให้บริการ EDC, รุ่นเครื่อง, สาขาที่อนุญาต |
| วิธีเชื่อมต่อ | LAN, USB, Bluetooth, local service หรือ API ของผู้ให้บริการ |
| ข้อมูลรายการ | amount, currency, order ID, terminal ID, merchant ID, idempotency key |
| ผลลัพธ์ | approved, declined, cancelled, timeout, unknown/pending |
| การคืนเงิน | void ก่อน settlement, refund หลัง settlement, partial refund ทำได้หรือไม่ |
| การปิดยอด | batch close, settlement reference, เวลา cut-off, reconciliation |
| ความปลอดภัย | ห้ามเก็บเลขบัตรเต็ม/PIN/CVV; เก็บเฉพาะ token/เลขอ้างอิงที่ผู้ให้บริการอนุญาต |
| อุปกรณ์สำรอง | ถ้าเครื่องหลักเสีย ต้องเปลี่ยน terminal อย่างไรโดยไม่ชำระซ้ำ |

### Use case สำหรับ EDC

| ID | กรณีทดสอบ | ขั้นตอน | ผลที่คาดหวัง |
|---|---|---|---|
| EDC-01 | ชำระบัตรสำเร็จ | POS ส่งยอด → ลูกค้าแตะ/เสียบ/รูด → อนุมัติ | EDC และ POS ได้ยอดเท่ากัน, มี approval/reference, ปิดบิลครั้งเดียว |
| EDC-02 | ลูกค้ายกเลิกที่เครื่อง | เริ่มจ่าย → กดยกเลิกบน EDC | POS ยังไม่ปิดบิล, ไม่มีใบเสร็จชำระสำเร็จ, ออเดอร์ยังค้นหาได้ |
| EDC-03 | ธนาคารปฏิเสธ | ใช้บัตร/ข้อมูลทดสอบที่จำลอง declined | แจ้งลูกค้าเข้าใจง่าย, ไม่ตัดเงินใน POS, เปลี่ยนช่องทางได้โดยไม่สร้างออเดอร์ใหม่ |
| EDC-04 | PIN ผิด/บัตรหมดอายุ/วงเงินไม่พอ | จำลองแต่ละสาเหตุ | แสดงผลปฏิเสธโดยไม่เปิดเผยข้อมูลลับ และไม่สร้าง payment สำเร็จ |
| EDC-05 | EDC timeout | POS ส่งยอดแล้วไม่ตอบกลับ | payment เป็น pending/unknown ไม่ใช่ failed ทันที; ต้องมีปุ่มตรวจสถานะ |
| EDC-06 | timeout แต่เงินจริงถูกตัด | ตรวจ transaction reference จาก EDC/ผู้ให้บริการ | POS ห้ามให้จ่ายซ้ำจน verify; reconcile แล้วผูก payment เดิมกับออเดอร์ |
| EDC-07 | กดปุ่มชำระซ้ำ | กดชำระบน POS หรือ refresh ระหว่าง EDC ทำงาน | ใช้ idempotency key เดิม, มีรายการเดียวและยอดเดียว |
| EDC-08 | ยอดบน EDC ไม่ตรง POS | เปลี่ยนยอดหรือส่ง request ผิดใน sandbox | EDC ต้องปฏิเสธ/หยุดรายการ และ POS ต้องไม่ปิดบิล |
| EDC-09 | EDC หลุดระหว่างอ่านบัตร | ถอด network/ปิดเครื่องจำลอง | POS แสดงสถานะชัดเจนและไม่สร้างรายการซ้ำเมื่อเชื่อมกลับ |
| EDC-10 | เปลี่ยนเครื่อง EDC สำรอง | เครื่องหลักเสีย → เลือก terminal สำรอง → ตรวจสถานะรายการเดิม | รายการเดิมถูกตรวจสอบก่อนเริ่มใหม่ และบันทึก terminal ID ที่ใช้จริง |
| EDC-11 | คืนเงินเต็มบิล | เลือกใบเสร็จเดิม → refund ผ่าน workflow | คืนได้ตามกติกา, อ้างอิง transaction เดิม, ไม่คืนซ้ำ |
| EDC-12 | คืนเงินบางรายการ | เลือกรายการบางส่วน → refund | จำนวนเงินคืนไม่เกินยอดเดิมและรายงานตรงกัน |
| EDC-13 | ยกเลิกก่อนปิดยอด | void transaction เดิมก่อน settlement | EDC และ POS เป็น void สำเร็จ มี reference และไม่ออกยอดขายสุทธิ |
| EDC-14 | คืนหลังปิดยอด | ทำ refund หลัง batch close | ใช้ refund workflow ของผู้ให้บริการ ไม่ใช้ void และมี settlement reference |
| EDC-15 | ปิดยอด EDC ประจำวัน | สั่ง batch close/settlement → เทียบรายงาน POS | ยอด approved, void, refund และยอดโอนตรงกัน หรือมีรายการต่างให้ตรวจ |
| EDC-16 | EDC อนุมัติแต่ POS ไฟดับ | ปิด POS หลัง EDC approved ก่อนรับ response | เปิด POS แล้วค้นหา/กระทบยอดจาก reference ไม่สร้างรายการใหม่ |
| EDC-17 | บัตร contactless และ chip | ทดสอบแตะและเสียบตามที่เครื่องรองรับ | ผลลัพธ์และ reference ถูกเก็บเหมือนกัน โดยไม่เก็บข้อมูลบัตรเกินจำเป็น |
| EDC-18 | ผู้ใช้ไม่มีสิทธิ์ refund/void | ให้พนักงานทดลองทำรายการ | ระบบปฏิเสธและบังคับหัวหน้ากะ/ผู้จัดการอนุมัติ |

### กฎสำคัญสำหรับพนักงานเมื่อ EDC ผิดปกติ

1. ถ้าเครื่องค้างหลังลูกค้ากดยืนยัน **ห้ามกดชำระใหม่ทันที**
2. จดเลขออเดอร์, ยอดเงิน, เวลา, terminal ID และ transaction/reference ที่หน้าจอ EDC แสดง
3. ตรวจเมนู **ตรวจสอบสถานะรายการ** หรือถามหัวหน้ากะก่อนเปลี่ยนช่องทางชำระ
4. ถ้าสถานะเป็น unknown ให้ถือว่ายังไม่สรุป ไม่ใช่ failed
5. ถ้า EDC อนุมัติแต่ POS ไม่ปิดบิล ให้ทำ reconciliation/ผูกผลเดิม ไม่สร้าง payment ใหม่
6. ห้ามถ่ายรูปหรือจดเลขบัตรเต็ม, PIN หรือ CVV

### เกณฑ์ผ่านก่อนใช้ EDC จริง

- [ ] ผู้ให้บริการรับรองรุ่นเครื่องและวิธีเชื่อมต่อกับ POS แล้ว
- [ ] ทดสอบ sandbox ครบ EDC-01 ถึง EDC-18 หรือระบุเหตุผลที่ไม่เกี่ยวข้อง
- [ ] ผ่านกรณี timeout/unknown และไฟดับหลังอนุมัติ โดยไม่เกิดการชำระซ้ำ
- [ ] ผ่าน void, refund, partial refund และ batch settlement
- [ ] ยอด POS เทียบกับรายงาน EDC/ธนาคารได้
- [ ] ไม่มีการเก็บเลขบัตรเต็ม, PIN หรือ CVV ในระบบ/log/ใบเสร็จ
- [ ] มีเครื่องสำรองและคู่มือหน้างาน 1 หน้า
- [ ] ฝ่ายบัญชีและผู้ให้บริการอนุมัติขั้นตอน reconciliation

## 16. การทดสอบโหลดและสถานการณ์ร้านยุ่ง

ทำในสภาพแวดล้อมทดสอบเท่านั้น:

- สร้างพร้อมกันอย่างน้อย 10 ออเดอร์จาก POS-01, POS-02 และ QR
- ให้แต่ละออเดอร์มีรายการครบ 4 สถานีและ modifier 2–3 รายการ
- กดยืนยัน/พิมพ์ซ้ำ/refresh ในช่วงเวลาใกล้กัน
- ทดสอบเครื่องพิมพ์หยุด 1 จุดระหว่างมีคิว 30 รายการ
- ตรวจว่าเลขออเดอร์ไม่ซ้ำ, ลำดับคิวไม่สลับ, รายงานไม่ตกหล่น, sync ไม่ซ้ำ และระบบยังใช้งานต่อได้

**เป้าหมายเริ่มต้นที่แนะนำ:** การกดยืนยันทั่วไปตอบสนองภายใน 2 วินาที, งานพิมพ์เข้าคิวภายใน 5 วินาที, การกู้คืนหลัง network กลับมาภายใน 2 นาทีสำหรับคิวเล็ก และไม่มีธุรกรรมซ้ำแม้กดซ้ำหรือ refresh

## 17. ตารางปัญหาและวิธีแก้สำหรับหน้างาน

| อาการ | ตรวจอะไรเป็นอันดับแรก | วิธีแก้เร็ว | ถ้ายังไม่หาย |
|---|---|---|---|
| Login ไม่ได้ | email, รหัส, สาขา, เวลาเครื่อง, network | login ใหม่/รีเซ็ตรหัสโดยแอดมิน | เก็บเวลาและข้อความ error ส่งผู้ดูแล |
| เมนูไม่ขึ้น | สาขา, active, effective time, cache | refresh หนึ่งครั้งและ logout/login | ตรวจ publish และ price book |

| ออเดอร์ไม่เข้าครัว | สถานี, printer, queue, network | ใช้ reprint จากออเดอร์เดิม | เปลี่ยนเครื่องสำรองและแจ้งครัว |

| ระบบค้าง | network, CPU/หน้าจอ, งานคิว | รอ 10 วินาที; เปิดเครื่องสำรอง | เก็บ screenshot และ correlation/order ID |

## 18. ขั้นตอนรับมือเมื่อพบปัญหา

1. **หยุดการทำซ้ำ:** อย่ากดซ้ำ อย่าสร้างออเดอร์ใหม่เพื่อกลบรายการเดิม และอย่าลบข้อมูล
2. **เก็บหลักฐาน:** เลขออเดอร์, เลขใบเสร็จ, payment reference, เวลา, เครื่อง, ผู้ใช้, ภาพหน้าจอ
3. **ทำงานต่อด้วยทางสำรอง:** ใช้ POS สำรอง, ใบครัวสำรอง, จด local order ID หรือรับเงินตามแผนฉุกเฉินของร้าน
4. **ตรวจสถานะก่อนแก้:** order, payment, print queue, stock ledger และ sync record ต้องดูจากรายการเดิม
5. **แก้ด้วย workflow ที่มีสิทธิ์:** refund, void, reprint, stock adjustment, retry หรือ conflict resolution
6. **ทดสอบซ้ำ:** ทำเคสเดิม 3 ครั้ง รวมกรณี refresh/กดซ้ำ/อุปกรณ์หลุด เพื่อยืนยันว่าแก้จริง
7. **ปิดปัญหาเมื่อมีหลักฐาน:** ระบุสาเหตุ, วิธีแก้ถาวร, ผู้รับผิดชอบ, เวอร์ชันที่แก้ และผลทดสอบ

### แบบฟอร์มแจ้งบั๊กฉบับสั้น

สิ่งที่เกิดจริง:

อุปกรณ์และสาขา:

ระดับ: P0 ร้านทำงานต่อไม่ได้ / P1 เงินหรือข้อมูลผิด / P2 ฟังก์ชันหลักบางส่วน / P3 ความสะดวก

## 20. Checklist เปิดร้านและปิดร้านแบบ 5 นาที

### เปิดร้าน

- [ ] Router/LAN/Wi-Fi ติดและเวลาเครื่องถูก
- [ ] POS-01/POS-02 login ได้และเลือกสาขาถูก
- [ ] เปิดกะและเงินทอนถูกต้อง
- [ ] เมนูขายวันนี้ active; เมนูหมดถูกปิด
- [ ] Test print ใบเสร็จ, ครัวร้อน, ครัวเย็น, ครัวย่าง, บาร์น้ำ
- [ ] กระดาษและหมึกพร้อม; ลิ้นชักเปิดปกติ
- [ ] QR โต๊ะตัวอย่างเปิดได้และไม่ข้ามสาขา
- [ ] ไม่มีคิว offline/sync ค้างจากวันก่อน

### ปิดร้าน

- [ ] ไม่มีออเดอร์ค้างหรือ payment pending
- [ ] ใบเสร็จ/ยอดขาย/ช่องทางชำระตรงกัน
- [ ] คืนเงิน/ยกเลิก/ส่วนลดเกินวงเงินมีผู้อนุมัติครบ
- [ ] นับเงินสดและบันทึก variance พร้อมเหตุผล
- [ ] ตรวจสต็อกผิดปกติและรายการปรับสต็อก
- [ ] ตรวจ print queue และ offline sync เป็นศูนย์หรือมีรายการส่งต่อ
- [ ] ปิดกะและส่งรายงานให้ผู้จัดการ

## 21. การแบ่งหน้าที่แบบเข้าใจง่าย (RACI)

| งาน | ผู้ทำ (R) | ผู้รับผิดชอบสุดท้าย (A) | ผู้ให้คำปรึกษา (C) | ผู้รับทราบ (I) |
|---|---|---|---|---|
| ทดสอบรับออเดอร์/ชำระเงิน | พนักงาน | หัวหน้ากะ | แอดมิน | ผู้จัดการ |
| ทดสอบครัวและบาร์ | พนักงานสถานีนั้น | หัวหน้าครัว | แอดมิน | ผู้จัดการ |
| ทดสอบเมนู ราคา ภาษี | แอดมิน | ผู้จัดการ | บัญชี/หัวหน้ากะ | พนักงาน |
| ทดสอบผู้ใช้และสิทธิ์ | แอดมิน | ผู้จัดการระบบ | ผู้จัดการร้าน | พนักงาน |
| ทดสอบอุปกรณ์ | ผู้ดูแลระบบ/ช่าง | ผู้จัดการร้าน | พนักงานจุดนั้น | ทีมพัฒนา |
| ตัดสินใจปิดบั๊ก | ผู้ทดสอบ | เจ้าของระบบ | ผู้จัดการสาขา | ทีมร้าน |

### หมายเหตุสำหรับผู้พัฒนาระบบ

ควรมี automated test รองรับอย่างน้อย: settlement ครั้งเดียวและ receipt reference, close shift และ variance, idempotent offline acknowledgement, conflict ไม่เขียนทับ local record, สิทธิ์/tenant isolation, stock ledger จาก BOM, payment timeout/retry และ printer routing โดย mock adapter ต้องไม่ส่งเงินจริงหรือข้อความจริง
